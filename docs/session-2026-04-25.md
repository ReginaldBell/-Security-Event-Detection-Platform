## 1. Scenario Validation Engine

### What It Does

The scenario engine closes the loop on detection quality. Instead of asking "does the detection engine work?" it asks "does the detection engine catch this specific attack pattern, at what confidence, and how fast?" The answer is a scored, repeatable result — not a manual observation.

### How It Works

A scenario runner fires a structured payload of synthetic authentication events at `POST /ingest/`. The ingest response returns full incident objects immediately. The validator checks whether an incident of the expected type was produced. The scorer measures wall-clock latency from POST to response and assigns a score (0–100).

### The 12-Scenario Suite (`scenarios/run_scenarios.py`)

12 scenarios across 4 detection axes. Each uses a distinct IP in the `10.0.1.x` block and distinct usernames to prevent cross-run state contamination in the incident store.

**Positive detection — fire and assert severity + confidence:**

| Scenario | Description | Expected type | Severity | Confidence |
|---|---|---|---|---|
| s01 | 5 failures, same ip+user | brute_force | low | 0.70 |
| s03 | 10 failures, same ip+user | brute_force | medium | 0.85 |
| s04 | 20 failures, same ip+user | brute_force | high | 0.95 |
| s07 | 10 failures across 5 users, same IP | credential_abuse | high | 0.90 |

**Negative / no-fire — detection engine respects its own boundaries:**

| Scenario | Description | Why it must not fire |
|---|---|---|
| s02 | 4 failures | One below brute_force threshold |
| s08 | 12 failures, 4 users | User count below credential_abuse threshold |
| s09 | 10 successes | Only failures count |
| s10 | 10 heartbeat events | Telemetry rejected before detection |
| s11 | 3 failures + 10 successes | Only 3 failures reach the engine |
| s12 | 5 failures, 5 distinct users | brute_force groups by (ip, user) — no pair reaches 5 |

**Window boundary pair — exercises strict `>` eviction:**

| Scenario | Span | Result | Reason |
|---|---|---|---|
| s05 | 61s | No-fire | Event at t=0 evicted when t=61 is processed |
| s06 | 60s | Fires | Event at t=0 still in window at t=60 (boundary is exclusive) |

### Results

```
12/12 passed  |  0 failed  |  avg 38.0ms  |  p95 57.1ms
```

Latency measured with `time.monotonic()` (wall-clock). No event-timestamp arithmetic.

### API Endpoint

```
POST /validate/{scenario_name}   # Run a named scenario, return validation + score
GET  /validate/results           # History of all validation runs
```

Scenario definitions live at `app/simulation/scenarios/{name}.json`.

## 2. Bug Fixes

### `app/simulation/runner.py` — Hardcoded INGEST_URL

**Before:** `INGEST_URL = "http://localhost:8000/ingest/"`

**After:** `INGEST_URL = os.environ.get("SECUREWATCH_INGEST_URL", "http://localhost:8000/ingest/")`

The validation endpoint calls `run_scenario()` internally, which POSTs to the ingest endpoint. Hardcoding localhost broke any deployment where the port or host differs. Now configurable via env var.

### `app/validation/scorer.py` — Broken Latency Calculation

**Before:** `latency = (datetime.fromisoformat(detection_time) - scenario_start).total_seconds()`

This compared `first_seen` (an event timestamp set by `datetime.utcnow()` inside the runner) against `scenario_start` (another `datetime.utcnow()` from the route). Both were called milliseconds apart, so latency was always near-zero and always scored +30. The number meant nothing.

**After:** The route measures wall-clock elapsed with `time.monotonic()` and passes `elapsed_seconds: float` directly to the scorer. Latency now reflects actual pipeline processing time.

### `scenarios/run_scenarios.py` — `_severity_confidence` Type Filtering

**Before:** The `_severity_confidence` closure iterated over all incidents in the response and checked severity/confidence against every one — not just the matched type.

**After:** Added `expected_type` as a first parameter. The closure now skips incidents that don't match the expected type, so assertions only apply to the incident that triggered the detection under test.

## 3. Docker Containerization

### Build

```bash
docker build -t securewatch .
docker compose up -d
```

### Verification

Scenario suite run against the container immediately after startup:

```
12/12 passed  |  0 failed  |  avg 38.0ms  |  p95 57.1ms
```

### Configuration

The `docker-compose.yml` exposes `SECUREWATCH_INGEST_URL` so the validation self-call is explicit:

```yaml
environment:
  - SECUREWATCH_INGEST_URL=http://localhost:8000/ingest/
```

The `./runs:/app/runs` volume mount persists incident state, run artifacts, and validation history across container restarts.

### Latency Context

Bare-metal run before containerization averaged ~2048ms per scenario. Container avg is 38ms. The bare-metal overhead was the incident store disk write going through the local Python dev server — not a detection engine issue. Container latency is the real baseline.

## 4. Post-Session Updates

### MITRE Coverage Endpoint

`GET /validate/results/mitre-coverage` aggregates all historical validation runs and returns a per-technique detection rate:

```json
{
  "T1110.003": { "tested": 4, "detected": 4, "success_rate": 100.0 },
  "T1110":     { "tested": 3, "detected": 3, "success_rate": 100.0 }
}
```

The technique is read from the scenario's `mitre` field (supports both string and object formats for forward compatibility). Benign scenarios (no `expected` detection type) are excluded from coverage stats.

### Wazuh Log Writer

Each validation run appends a structured JSON line to `runs/securewatch_wazuh.log` (path configurable via `WAZUH_LOG_PATH` env var):

```json
{
  "rule_id": "securewatch_validation",
  "timestamp": "2026-04-25T23:00:00",
  "scenario": "password_spray_01",
  "detected": true,
  "false_positive": false,
  "score": 100,
  "latency_seconds": 0.038
}
```

This log is Wazuh-ingestible via a `localfile` block on siem01, enabling Wazuh to alert on validation failures or false positives as part of the live detection pipeline.

### False Positive Handling

The scorer now handles a third outcome — `false_positive` — for benign scenarios where the engine incorrectly fires. Status returns `"false_positive"` with score 0 rather than conflating it with a missed detection (`"fail"`).
